# Benchmarks

Real wall-clock measurements of MoeSOC's own pipeline. The **events are synthetic**
(generated by `scripts/benchmark.py`: logons and failures for 250 test accounts from
documentation addresses, with a brute-force burst every 2,000 events); the **timings are
real**, measured on the machines below. Nothing here is estimated or extrapolated.

Each run uses a throwaway SQLite file in a temporary folder; the real MoeSOC database and
the Windows event logs are not touched. Reading from the Windows Event Log API itself is
**not** part of these numbers (it depends on the log, its size and the disk); see
"What is not measured".

## Stages

| Stage | What is timed |
|---|---|
| Parse | rendered XML → normalized events (`parse_any_xml`) |
| Store | insert into SQLite, one transaction, duplicates ignored |
| Detect | load the 25-hour detection window and run every rule plus the risk model, store findings |
| Search | three paginated searches: user contains, IP prefix, free text |
| Story | build the investigation story of the largest finding |
| Report | render that finding's HTML report |

## What the numbers say

- **Parse and detect scale about linearly** from 10k to 100k events (≈ 10× time for 10× events on both machines).
- **Store grows faster than linear** at the top end: on the Windows PC 10k → 100k events took 0.32 s → 5.39 s (≈ 17×); on Linux 0.35 s → 3.94 s (≈ 11×). The likely cause is index maintenance as the table grows (events have 15+ indexes for search and correlation). Still about 18,000 events/s at 100k on the PC; worth revisiting if larger scans are needed.
- **A full scan budget is seconds, not minutes.** The default per-scan cap is 50,000 events; on the Windows PC parse + store + detect of 100,000 events took 17.6 s in total (14,144 events/s for detection).
- **Investigation views stay interactive.** Search, story and report take milliseconds to a few hundred milliseconds even at 100k stored events, because they run in SQLite with indexes and pagination.
- **Storage cost is about 1.8 KB per event**, mostly the raw event XML kept for evidence and the raw-XML viewer (176 MB per 100,000 events). Retention (Settings, default 30 days) bounds growth.
- The two machines are close at small sizes; at 100k the PC is faster for parse (5.1 s vs 6.4 s) and detect (7.1 s vs 8.8 s) but slower for store (5.4 s vs 3.9 s).

## What is not measured

- Reading the Windows Event Log (`EvtQuery`/`EvtNext`/`EvtRender`) — depends on log size, filters and disk. Incremental collection keeps this to new records only.
- Live monitoring latency (batching waits for 2 s of quiet by design).
- GUI rendering time.
- Memory use (not instrumented yet).

## Reproduce

```powershell
scripts\benchmark.bat                      # Windows: writes benchmark_output.txt and docs\benchmarks\windows-pc.json
python scripts/benchmark.py --sizes 1000 10000 --json my-run.json
```
